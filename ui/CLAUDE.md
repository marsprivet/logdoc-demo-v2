# LogDoc UI: правила для AI-агента

Фронтендера нет. Дизайнер ставит задачу и принимает результат в браузере,
а код пишешь ты. Каждый экран собирай из дизайн-системы `src/ds` и не
придумывай собственный визуальный язык.

## Компоненты

- Сначала бери компонент из `src/ds/components`. Импортируй по одной папке:
  `import { Button } from "@ds/components/button";`. Никогда не импортируй
  из общего `@ds/components`: так в бандл попадает вся библиотека.
- Иконки бери только из `@ds/icons`. Никаких инлайновых SVG и сторонних
  наборов иконок.
- Не используй нативные `<select>`, `<input type=checkbox|radio>`,
  `window.confirm()`, `window.prompt()` и `alert()`. Вместо них есть Select,
  Checkbox, RadioGroup, ConfirmDialog и Dialog из ds.
- Боковые карточки на карте делай через `DrawerWrapper`: без модальности и
  без оверлея, чтобы карта оставалась живой.
- Если в ds нет подходящего компонента, собери композицию LogDoc в
  `src/components` из примитивов ds (так сделаны `LevelBadge` и
  `SearchInput`) и добавь к ней стори. Саму `src/ds` правь, только когда
  об этом просит дизайнер.

## Стили

- Цвета, радиусы, шрифты и отступы бери только из токенов:
  `--l1/l2/l3-background`, `--l1/l2/l3-foreground`, `--l2/l3-border`,
  `--accent-primary`, `--radius`, `--font-mono` и статусные палитры
  `--bg-<цвет>-<шаг>`. Никаких hex, rgb и именованных цветов в коде.
- Для уровней логов используй только переменные `--level-*` из `global.css`.
- Внешний отступ страницы один на все экраны: `--page-padding`. Свои
  внешние отступы не добавляй.
- У контролов в тулбаре одна высота: md (32px) для Button, ToggleGroup,
  Input и чипов. Не смешивай sm и md в одной строке.
- Подписи секций в строках фильтров делай классом `.sect` (`// period`,
  `// node type`). Строки — это `.toolbar` и `.filter-row`.
- Стили одного экрана живут в его `<Name>.css` рядом с `.tsx`, общая
  раскладка приложения — в `global.css`. Инлайновый `style={{}}` допустим
  только для вычисляемых значений (координаты, ширины).

## Порядок работы

1. Прежде чем писать код, перескажи задачу в одном-двух предложениях и
   перечисли компоненты ds, которые возьмёшь. Если задача неоднозначна,
   спроси, а не угадывай.
2. Одна задача — один коммит. Не чини попутно то, о чём не просили:
   перечисли такие находки в конце ответа.
3. Сам проверь результат в браузере до того, как отчитываться:
   - `ui-dev` из `.claude/launch.json` поднимает приложение, `storybook` —
     компоненты;
   - для карты топологии загрузи демо-данные из `deploy/demo-declared.py`
     (~40 сервисов): на редком графе проблем не видно;
   - посмотри консоль и сеть, сделай скриншот.
4. Перед коммитом запусти `npm run build` (tsc + vite) и включи в коммит
   пересобранный `ui/dist`: Go-бинарник вшивает его в себя.
5. Сообщение коммита — это заголовок в повелительном наклонении короче
   60 символов и тело: что изменилось для пользователя и зачем. В
   заголовке не должно быть жаргона, которого не поймёт дизайнер.

## Что не трогать

- Бэкенд (`cmd/`, `internal/`, `pkg/`) и API. Если UI не хватает данных
  из API, скажи об этом, а не делай обходной путь на клиенте.
- Токены и тему (`src/ds/tokens`). Меняй их только по просьбе дизайнера и
  после правки запускай `npm run tokens`.
- Правки, которые дизайнер уже принял. Когда переносишь новый экран из
  основного репозитория, проверь, что такие правки пережили перенос.
  Пример — обводка подписей на карте, см. `TOPOLOGY_LABEL_FIX.md`.

## Отчёт

Коротко: что сделал, какой экран открыть, чтобы это увидеть, скриншот и
что оставил в стороне или в чём сомневаешься.
